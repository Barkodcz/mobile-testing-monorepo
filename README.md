# Mobile Testing Monorepo

## What this is

A reference monorepo for **configuring mobile testing frameworks on Bitrise**. It holds one
sample counter app per platform (native Android, native iOS, React Native, Flutter), each wired
up with every common test type for that platform/framework — unit, snapshot, instrumented/UI, and
cross-platform E2E — plus video recording where the framework supports it and automatic reporting
to Bitrise's **Tests tab**.

Use this repo to:
- see a concrete, working example of a specific framework's Bitrise setup before building your
  own (one YAML module + one doc per platform — start with the [framework matrix](#framework-matrix)
  below to find the one you need),
- copy the reusable pieces (the [attachment-naming trick](docs/BITRISE_CONCEPTS.md#4-the-attachment-naming-convention),
  the recording scripts, `attach_media_to_junit.py`) into your own project,
- understand *why* each setup looks the way it does — every non-obvious decision and every bug hit
  along the way is documented, not just the final config.

It is not a real product; the four sample apps are intentionally as small as possible (a counter:
increment, decrement, reset) so the *testing setup* is the only thing worth looking at.

## The example apps

All four apps are functionally identical — the same counter, the same four interactive elements
(`count_label`, `decrement_button`, `increment_button`, `reset_button`) — so the exact same E2E
journeys (Maestro flows, Appium tests) can be written once and ported across platforms with
minimal changes.

| App | What it does |
|---|---|
| `apps/android` | Native Android (Jetpack Compose) counter app |
| `apps/ios` | Native iOS (SwiftUI) counter app, Xcode project generated by XcodeGen |
| `apps/react-native` | React Native counter app, same UI on both platforms |
| `apps/flutter` | Flutter counter app, same UI on both platforms |

Each has its own short README (linked from the repo map below) and its own `BITRISE.md`-style doc
documenting its CI setup in full.

## How to set up any project here on Bitrise

1. **Add the app**: in the Bitrise dashboard, add a new app and connect this repository.
2. **Monorepo handling**: there's no separate "project path" field to configure — this repo uses
   one root `bitrise.yml` that `include:`s one YAML module per platform from `bitrise/`, and every
   Step inside each workflow sets its own `working_dir` to the relevant `apps/<platform>`
   subfolder. Point Bitrise at the repo root for its config file location.
3. **Enable file-based config**: `include:`-based config modules need to be *stored in the repo*
   (not pasted into the Bitrise web UI's own editor), which requires an **Enterprise-plan**
   workspace — see [`BITRISE.md`](BITRISE.md) §2.
4. **Stack and machine**: already set sensibly per workflow (Linux by default, Mac only where
   Xcode/Simulator is actually needed) — nothing to configure unless you add a new workflow.
5. **Secrets and env vars**: add `BROWSERSTACK_USERNAME`/`BROWSERSTACK_ACCESS_KEY` (for
   `appium_browserstack`) under the app's **Secrets**, and enable the **Virtual Device Testing**
   add-on (for `android-espresso-vdt`) under **Add-ons**. No other external credential is needed
   anywhere in this repo — see [`BITRISE.md`](BITRISE.md) §4 for the full list of app-level env
   vars (none of which are secret values).
6. **Trigger the first build**: push to `main` or open a PR touching `apps/<platform>/**` — the
   matching pipeline triggers automatically (see [concepts §2](docs/BITRISE_CONCEPTS.md#2-triggers)).
   Or start any workflow/pipeline manually from the Bitrise UI (**Start build**) without waiting
   for a matching change — most of the "secondary approach" workflows in this repo (e.g. the
   manual-only XCUITest variants) are meant to be started this way.
7. **Verify it actually worked**: [`docs/TEST_VERIFICATION_GUIDE.md`](docs/TEST_VERIFICATION_GUIDE.md)
   has the full pipeline/workflow inventory, exact pass criteria per workflow, and a repeatable
   full-sweep procedure — use it instead of eyeballing one green checkmark and assuming the rest
   works too.

## Shared concepts

Explained once in [`docs/BITRISE_CONCEPTS.md`](docs/BITRISE_CONCEPTS.md): workflows vs. pipelines,
triggers, the Tests tab + attachment-naming convention, the `cp -r` vs. `zip` artifact-deploy
gotcha, caching, and step-version pinning. Every per-module doc links there instead of repeating
it.

## Conventions

- **Doc location**: every `bitrise*.yml` gets a doc in the *same folder*, named `BITRISE.md` if
  it's the only YAML in that folder, or `<yml-name>.md` if the folder holds several (that's why
  `bitrise/` has five `.md` files but the root has one `BITRISE.md`). Every sample app folder gets
  its own short `README.md` linking to its CI doc.
- **Step pinning**: every Bitrise Step is pinned to an exact version, never a floating major — see
  [concepts §9](docs/BITRISE_CONCEPTS.md#9-step-version-pinning).
- **Official Steps over `script`, and Step bundles for repeated sequences**: every `script` Step in
  this repo was checked against the Bitrise StepLib for an official replacement, and repeated Step
  sequences (AVD creation, iOS simulator boot) were factored into Step bundles — see
  [concepts §6](docs/BITRISE_CONCEPTS.md#6-official-steps-vs-script) and
  [§7](docs/BITRISE_CONCEPTS.md#7-step-bundles).
- **Element IDs**: every sample app exposes the same four element IDs
  (`count_label`/`decrement_button`/`increment_button`/`reset_button`) via its platform's native
  accessibility/test-tag mechanism. Keep this convention when adding a new sample app so Maestro
  flows and Appium locators can be reused.
- **Adding a new framework/example**: pick (or add) the platform's `apps/<platform>` app, add a
  new Bitrise workflow to that platform's `bitrise/<platform>.yml` (reuse `scripts/recording/*`
  and `scripts/reporting/attach_media_to_junit.py` wherever the framework doesn't provide its own
  video/screenshot attachment natively), then update that module's `.md` doc (one workflow section
  following the same 9-part structure every other workflow uses) and this README's framework
  matrix.

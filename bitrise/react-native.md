# React Native CI (`bitrise/react-native.yml`)

This document fully explains the Bitrise config module for the React Native sample app
(`apps/react-native`, a one-screen "CounterRN" app). It is included into the root
[`bitrise.yml`](../bitrise.yml) via `include: - path: bitrise/react-native.yml`.

For Bitrise concepts that are generic to every module in this repo — workflows vs. pipelines,
triggers, the Tests-tab attachment-naming convention, `deploy-to-bitrise-io`, caching, and
step-version pinning — see [`../docs/BITRISE_CONCEPTS.md`](../docs/BITRISE_CONCEPTS.md) rather
than this file.

## 1. Overview

`bitrise/react-native.yml` builds and tests the React Native counter app three independent
ways:

- **Jest** unit/component tests (`rn_jest_tests`) — plain JS, no simulator, runs on Linux.
- **Detox** E2E tests on a real iOS Simulator (`rn_detox_ios`) — builds and drives a Release
  iOS build of the app.
- **Maestro** E2E tests against the same user journeys, run twice: once against an **Android**
  build (`android-maestro-e2e-rn`) and once against an **iOS** build
  (`ios-maestro-e2e-rn`) — so the same flow files demonstrate Maestro's cross-platform story
  and can be compared directly against the Detox suite.

A reader triggering a build on this module should expect to see, on the Bitrise **Tests** tab:
a `Jest (React Native)` suite with each `it()` as its own test case; a `Detox E2E (iOS)` suite
with each Detox `it()` as its own test case, with screenshots/video/logs attached per case; and
(for the two manual Maestro workflows) a `Maestro E2E (React Native / Android|iOS)` suite with
one test case per flow file, each carrying its own recording, screenshot, and command log. On
the **Artifacts** tab: an npm cache, a zipped copy of the full Detox `test-results` folder, and
the Maestro output zip.

## 2. Prerequisites

### Stack / machine per workflow

| Workflow | Stack | Machine | Why |
|---|---|---|---|
| `rn_jest_tests` | inherited from root `bitrise.yml`: `ubuntu-noble-24.04-bitrise-2025-android` | `g2.linux.medium` | Pure JS tests need no simulator/emulator — cheapest machine. |
| `rn_detox_ios` | `osx-xcode-27.2.x` | `g2.mac.medium` | Needs an iOS Simulator and Xcode toolchain (Xcode 27.2.x per the stack id) for the Detox build. |
| `android-maestro-e2e-rn` | `ubuntu-noble-24.04-bitrise-2025-android` | `g2.linux.large` | Needs an Android emulator (AVD Manager); `large` for Gradle + emulator boot headroom. |
| `ios-maestro-e2e-rn` | `osx-xcode-27.2.x` | `g2.mac.medium` | Needs Xcode + iOS Simulator for the `xcodebuild` build. |

### Tools / versions

- **Node** ≥ 22.11.0 (`apps/react-native/package.json` `engines.node`); installed implicitly by
  the stack's preinstalled Node/npm (the `npm@3.1.0` step uses whatever npm/corepack resolves
  on the stack, pinned via `package.json`'s `packageManager` field if present — this repo
  relies on the stack default).
- **CocoaPods**: version resolved by the `cocoapods-install@3.1.1` step from
  `apps/react-native/ios/Podfile.lock` (not committed — generated by `pod install`) /
  `Gemfile.lock`, constrained by
  [`apps/react-native/Gemfile`](../apps/react-native/Gemfile) (`cocoapods >= 1.13, != 1.15.0, != 1.15.1`).
- **Xcode**: whatever version ships with the `osx-xcode-27.2.x` stack (used by both
  `rn_detox_ios` and `ios-maestro-e2e-rn`).
- **Android build tools**: whatever the `ubuntu-noble-24.04-bitrise-2025-android` stack
  preinstalls, plus an AVD created on the fly by `avd-manager@2.2.0` (API level 34,
  `google_apis`, `x86_64`, `pixel_6` profile) for `android-maestro-e2e-rn`.
- **Detox CLI** `^20.51.4` and **jest-junit** `^17.0.0` — both devDependencies installed by
  `npm ci` (see [`apps/react-native/package.json`](../apps/react-native/package.json)).
- **Maestro CLI** `2.12.1` — installed by the `maestro-test@1.2.0` step itself, not by
  `npm`/Homebrew.
- **applesimutils** — installed ad hoc inside the `rn_detox_ios` script via
  `brew tap wix/brew && brew install wix/brew/applesimutils` if not already present (Detox's
  iOS simulator helper).

### Secrets / env vars used

| Name | Purpose |
|---|---|
| `RECORD_VIDEO` | App-level env (root `bitrise.yml`, default `all`). Controls video-keeping policy across every workflow: `all`\|`failures`\|`off`. Mapped to Detox's own `--record-videos` flag in `rn_detox_ios`; Maestro always records (`startRecording`/`stopRecording` in the flow files) regardless of this var — see §5. |
| `BITRISE_SOURCE_DIR` | Bitrise-provided; the cloned repo root. Used throughout to anchor `workdir`/`working_dir`/paths into `apps/react-native`. |
| `BITRISE_DEPLOY_DIR` | Bitrise-provided; where `deploy-to-bitrise-io` picks up artifacts. Used directly in `rn_detox_ios`'s zip step. |
| `BITRISE_APP_DIR_PATH` | Custom env created with `envman add` inside `ios-maestro-e2e-rn`'s build script, carrying the built `.app` path to the codesign step and to `maestro-test`'s `app_path` input. Not a secret — a same-workflow step-to-step handoff. |
| `MAESTRO_APP_ID` | Passed as `-e MAESTRO_APP_ID=...` via `maestro-test`'s `additional_args` input in both Maestro workflows, consumed by `appId: ${MAESTRO_APP_ID}` in the flow YAML files. Android: `com.counterrn`; iOS: `org.reactjs.native.example.CounterRN`. Not a Bitrise secret — a literal baked into each workflow's step config. |
| `BITRISE_BUILD_URL` / `BITRISE_BUILD_API_TOKEN` | Bitrise-provided defaults consumed implicitly by `deploy-to-bitrise-io` (not explicitly set in this file; listed because the step reads them). |

No app-specific secrets (signing credentials, API keys) are required: `rn_detox_ios` and
`android-maestro-e2e-rn` both produce unsigned/debug-signed builds, and `ios-maestro-e2e-rn`
explicitly disables signing (`CODE_SIGNING_ALLOWED=NO`) and ad-hoc codesigns the result instead
of using a real certificate.

## 3. Triggers and pipelines

Only one pipeline references this module's workflows: `react_native`, defined in this same
file.

```yaml
pipelines:
  react_native:
    workflows:
      rn_jest_tests: {}
      rn_detox_ios:
        depends_on: [rn_jest_tests]
    triggers:
      push: [{ branch: main, changed_files: {...} }]
      pull_request: [{ draft_enabled: false, changed_files: {...} }]
```

- **`rn_jest_tests`** has no dependency — it always starts immediately.
- **`rn_detox_ios`** declares `depends_on: [rn_jest_tests]`, so it only starts after
  `rn_jest_tests` completes, and (per Bitrise pipeline semantics) only runs at all if
  `rn_jest_tests` succeeded — "only spend macOS minutes if Jest is green" per the file's own
  comment on line 9.
- **Triggers**: a push to `main` or a non-draft PR, but only when changed files match
  `^(apps/react-native/.*|bitrise/react-native\.yml)$` — i.e., changes under the RN app itself
  or to this config file. Changes elsewhere in the monorepo do not start this pipeline.
- **`android-maestro-e2e-rn`** and **`ios-maestro-e2e-rn`** have **no triggers at all** and are
  **not** members of the `react_native` pipeline — they are manual-trigger-only workflows,
  started directly from the Bitrise UI (Start build → Workflow). This is a deliberate choice
  (per both workflows' `summary:` blocks) to avoid spending emulator/simulator minutes on every
  push on top of the Detox suite that already covers equivalent ground.
- The root `bitrise.yml`'s `everything_fast` manual pipeline includes `rn_jest_tests` (but not
  the Detox or Maestro workflows, since those need non-default machines/stacks and are not
  "fast").

## 4. Workflow-by-workflow walkthrough

### 4.1 `rn_jest_tests`

> Jest unit, component and snapshot tests (Linux, no simulator).

1. **`git-clone@8.5.2`** — *Git Clone Repository*. Checks out the repo at the triggering
   commit/PR merge ref. No inputs overridden; uses the standard Bitrise trigger-driven
   defaults (`$BITRISE_GIT_BRANCH`, `$BITRISE_GIT_COMMIT`, etc.).
2. **`restore-npm-cache@3.0.2`** — *Restore NPM Cache*. Restores a previously saved
   `node_modules` cache (key-based, set up automatically for npm/Yarn). No inputs set; paired
   with `save-npm-cache` later in the same workflow. Output `BITRISE_CACHE_HIT` is not consumed
   downstream.
3. **`npm@3.1.0`** — *Run npm command*. Inputs: `workdir: $BITRISE_SOURCE_DIR/apps/react-native`,
   `command: ci`. Runs `npm ci` in the RN app folder, installing exact `package-lock.json`
   versions (devDependencies included) — the fresh/clean counterpart to the restored cache.
4. **`script@1.2.1`**, titled "Run Jest". `working_dir` is the RN app folder.
   ```bash
   set -eo pipefail
   # jest.config.js adds the jest-junit reporter -> test-results/jest-junit.xml
   npx jest --ci
   ```
   - `set -eo pipefail` — abort the script (and fail the step) on the first failing command or
     failing stage of a pipe.
   - `npx jest --ci` — runs Jest in CI mode (disables interactive watch behavior, uses more
     conservative snapshot-write defaults). The reporter config living in
     [`apps/react-native/jest.config.js`](../apps/react-native/jest.config.js) adds `jest-junit`
     alongside the `default` reporter, writing `test-results/jest-junit.xml` relative to the
     `working_dir` (i.e. `apps/react-native/test-results/jest-junit.xml`).
5. **`custom-test-results-export@2.0.0`** (*Export test results to Test Reports*),
   `is_always_run: true`. Inputs: `test_name: Jest (React Native)`,
   `base_path: $BITRISE_SOURCE_DIR/apps/react-native/test-results`,
   `search_pattern: "*/jest-junit.xml"`. Searches under `base_path` for files matching the
   pattern, builds the `test-info.json` + copies the XML into Bitrise's test-result staging
   area so the later `deploy-to-bitrise-io` step can push it to the **Tests** tab under the
   "Jest (React Native)" tab name. `is_always_run: true` so results still surface even if the
   Jest step itself failed.
6. **`save-npm-cache@1.2.1`** — *Save NPM Cache*. Writes the `node_modules` cache for next
   run's `restore-npm-cache` to pick up. Not `is_always_run`, so a failed earlier step skips
   this (acceptable — nothing changed worth re-caching if `npm ci` itself failed).
7. **`deploy-to-bitrise-io@2.26.2`**, `is_always_run: true`. No inputs overridden. Uploads
   everything staged under `$BITRISE_DEPLOY_DIR` as build artifacts and converts/ships the
   staged test-result data (from step 5) to the **Tests** tab. `is_always_run: true` ensures
   results/artifacts are published even on failure.

### 4.2 `rn_detox_ios`

> Detox E2E tests on an iOS simulator (release build).

Runs on `osx-xcode-27.2.x` / `g2.mac.medium` (overridden via workflow-level `meta`, since the
root default is a Linux stack).

1. **`git-clone@8.5.2`** — same as above.
2. **`restore-npm-cache@3.0.2`** — same mechanism as above, independent cache lane (keyed per
   workflow/stack by the step itself).
3. **`npm@3.1.0`** — `workdir: .../apps/react-native`, `command: ci`. Same `npm ci` as above.
4. **`cocoapods-install@3.1.1`** — *Run CocoaPods install*. Input: `source_root_path:
   $BITRISE_SOURCE_DIR/apps/react-native/ios`. Runs `pod install` (default `command`) in the
   iOS project folder, resolving the CocoaPods version from `apps/react-native/ios/Podfile.lock`
   (not committed — generated by `pod install`) / [`Gemfile.lock`](../apps/react-native/Gemfile),
   per the Gemfile's version constraints.
5. **`script@1.2.1`**, titled "Build and run Detox". `working_dir`: RN app folder.
   ```bash
   set -eo pipefail
   command -v applesimutils >/dev/null 2>&1 || { brew tap wix/brew && brew install wix/brew/applesimutils; }
   npx detox build --configuration ios.sim.release
   case "${RECORD_VIDEO:-failures}" in
     all) DETOX_VIDEO_MODE=all ;;
     off) DETOX_VIDEO_MODE=none ;;
     *) DETOX_VIDEO_MODE=failing ;;
   esac
   npx detox test --configuration ios.sim.release --cleanup --record-logs failing \
     --take-screenshots all --record-videos "$DETOX_VIDEO_MODE"
   ```
   - Installs `applesimutils` (Detox's Wix-maintained simulator helper CLI) only if missing —
     idempotent, keeps the Homebrew install off the hot path on a cached/preinstalled image.
   - `npx detox build --configuration ios.sim.release` builds the app per the
     `ios.sim.release` configuration in `.detoxrc.js` (see below) — this is a **Release** Xcode
     build, not Debug. The inline comment captures why: a Debug RN build depends on the Metro
     bundler being up to render anything; a build driven externally by Detox/Maestro has no
     Metro process attached, so only a Release build (JS bundle embedded) will actually render
     the UI.
   - The `case` statement maps the app-level `$RECORD_VIDEO` (`all`\|`failures`\|`off`, default
     `all` from root `bitrise.yml`; the script's own fallback is `failures` if unset) onto
     Detox's native video-artifact plugin modes (`all`\|`failing`\|`none`).
   - `npx detox test ...`: `--cleanup` terminates/uninstalls at the end; `--record-logs failing`
     keeps device logs only for failing tests; `--take-screenshots all` takes a screenshot
     after every test regardless of outcome (the inline comment notes the explicit
     `device.takeScreenshot()` calls in `counter.e2e.js` would otherwise be no-ops on disk
     under "failing" mode unless the test actually failed — `all` forces them to be saved);
     `--record-videos "$DETOX_VIDEO_MODE"` applies the mapped mode from above.
   - This step reads [`apps/react-native/.detoxrc.js`](../apps/react-native/.detoxrc.js):
     `apps['ios.release'].binaryPath` is `ios/build/Build/Products/Release-iphonesimulator/CounterRN.app`,
     built via the inline `build:` command (another `xcodebuild ... -configuration Release`);
     `devices.simulator` targets an `iPhone 16` simulator; `testRunner` points Detox's Jest
     runner at `e2e/jest.config.js`.
6. **`custom-test-results-export@2.0.0`**, `is_always_run: true`. Inputs: `test_name: Detox
   E2E (iOS)`, `base_path: .../apps/react-native/test-results`, `search_pattern:
   "*/detox-junit.xml"`. Picks up the JUnit file written by `e2e/jest.config.js`'s `jest-junit`
   reporter (`test-results/detox-junit.xml`) and stages it for the Tests tab under "Detox E2E
   (iOS)". Screenshot/video/log attachments are matched to test cases by filename convention —
   see §5.
7. **`script@1.2.1`**, titled "Keep Detox artifacts as a browsable zip too", `is_always_run:
   true`.
   ```bash
   zip -qr "$BITRISE_DEPLOY_DIR/detox-artifacts.zip" apps/react-native/test-results 2>/dev/null || true
   ```
   Zips the entire `test-results` tree (screenshots, videos, logs, both JUnit XMLs) into the
   deploy dir as a single browsable artifact. The inline comment explains why: `deploy-to-bitrise-io`
   only picks up **files**, not raw copied directories, from the deploy dir, so a directory of
   artifacts needs to be archived first if you want it browsable as one unit on the Artifacts
   tab (separately from the per-test-case attachments that `custom-test-results-export` already
   wired up in step 6). `|| true` swallows a non-zero `zip` exit (e.g. nothing to zip) so this
   never fails the build.
8. **`save-npm-cache@1.2.1`** — same as above.
9. **`deploy-to-bitrise-io@2.26.2`**, `is_always_run: true` — same as above; ships both the
   zip artifact and the staged test-result data.

### 4.3 `android-maestro-e2e-rn`

> Maestro flows against the React Native app's Android build. Manual-trigger only, not in the
> `react_native` pipeline.

Runs on `ubuntu-noble-24.04-bitrise-2025-android` / `g2.linux.large` (workflow-level `meta`
override, matching the root default stack but a larger machine).

1. **`git-clone@8.5.2`** — same as above.
2. **`restore-npm-cache@3.0.2`** — same mechanism.
3. **`npm@3.1.0`** — `npm ci` in `apps/react-native`.
4. **`bundle::android_avd_create`** — Step bundle ([`bitrise/common.yml`](../bitrise/common.yml), see
   [`docs/BITRISE_CONCEPTS.md`](../docs/BITRISE_CONCEPTS.md) §7; previously an inline
   `avd-manager@2.2.0` here), default inputs: `avd_profile: pixel_6`, `avd_api_level: "34"`,
   `avd_tag: google_apis`, `avd_abi: x86_64`. Creates and boots an Android Virtual Device matching a
   Pixel 6 on API 34 with Google APIs, x86_64 (suitable for the Linux CI host, which can't run
   ARM images at reasonable speed without nested virtualization).
5. **`android-build@1.2.0`** — *Android Build*. Official Step; replaced a
   `./gradlew :app:assembleRelease` script. Inputs: `project_location:
   $BITRISE_SOURCE_DIR/apps/react-native/android`, `module: app`, `variant: release`.
   Builds the **Release** variant of the Android app, exporting its path as `$BITRISE_APK_PATH`.
   The YAML's own comment (kept as a standalone comment above the step since the Step itself has
   no `title` input) is explicit about why Release and not Debug: "debug builds need the Metro
   bundler running to render anything (classic RN gotcha — confirmed live: a debug APK here
   showed neither 'Count: 0' nor increment_button at all)." It also notes the project's release
   `signingConfig` already points at the debug keystore, so the Release APK installs without
   needing real signing credentials.
6. **`wait-for-android-emulator@1.0.10`** — *Wait for Android emulator*. No inputs overridden
   (defaults to `$BITRISE_EMULATOR_SERIAL`, the output of step 4). Blocks until the AVD created
   in step 4 finishes booting, before Maestro tries to install/launch on it.
7. **`maestro-test@1.2.0`** — *Maestro Test*. Inputs:
   - `app_path: $BITRISE_APK_PATH` — the built release APK's path, exported natively by the
     preceding `android-build@1.2.0` step.
   - `flow_path`: `.../apps/react-native/maestro` (the whole flow directory; the directory's
     own [`config.yaml`](../apps/react-native/maestro/config.yaml) just says "run every
     `*.yaml`").
   - `test_name: Maestro E2E (React Native / Android)` — names the Tests-tab suite.
   - `maestro_version: 2.12.1` — pins the Maestro CLI version the step installs.
   - `num_flaky_test_attempts: 1` — one automatic retry of a failed flow before it's reported
     as failed.
   - `additional_args: -e MAESTRO_APP_ID=com.counterrn` — passes the Android package id as a
     Maestro environment variable, consumed by `appId: ${MAESTRO_APP_ID}` at the top of each
     flow YAML. The README and inline comments explain the "why": `maestro test` has no
     `--app-id` CLI flag (confirmed to fail live with "Unknown option: '--app-id'"), so
     parameterizing the flow file's own `appId:` field via `-e` is the only way to run one set
     of flow files against two different platform-specific bundle/package ids.
   - Per the step's own description, this step installs the app on the already-running
     device, runs `maestro test`, and exports results (with screenshots/`startRecording`
     videos/logs attached per test case, and the commands run as a step list) plus a zip of the
     Maestro output folder.
8. **`save-npm-cache@1.2.1`** — same as above.
9. **`deploy-to-bitrise-io@2.26.2`**, `is_always_run: true` — same as above.

### 4.4 `ios-maestro-e2e-rn`

> Same Maestro flows as `android-maestro-e2e-rn`, against the iOS build. Manual-trigger only.

Runs on `osx-xcode-27.2.x` / `g2.mac.medium`.

1. **`git-clone@8.5.2`** — same as above.
2. **`restore-npm-cache@3.0.2`** — same mechanism.
3. **`npm@3.1.0`** — `npm ci` in `apps/react-native`.
4. **`cocoapods-install@3.1.1`** — `source_root_path: .../apps/react-native/ios`; same as in
   `rn_detox_ios`.
5. **`script@1.2.1`**, titled "Build for simulator (raw xcodebuild build, not archive)".
   ```bash
   set -eo pipefail
   xcodebuild build \
     -workspace apps/react-native/ios/CounterRN.xcworkspace \
     -scheme CounterRN \
     -configuration Release \
     -sdk iphonesimulator \
     -destination "platform=iOS Simulator,name=Bitrise iOS default,OS=latest" \
     -derivedDataPath "$BITRISE_SOURCE_DIR/ios-sim-build" \
     CODE_SIGNING_ALLOWED=NO
   APP_PATH="$(find "$BITRISE_SOURCE_DIR/ios-sim-build/Build/Products" -maxdepth 2 -name 'CounterRN.app' | head -1)"
   envman add --key BITRISE_APP_DIR_PATH --value "$APP_PATH"
   ```
   - Builds directly with `xcodebuild build` rather than an archive-oriented step. The inline
     comment explains the pitfall this avoids: the `xcode-build-for-simulator` step's `xcodebuild
     archive` subcommand tags the product for the device platform regardless of
     `-destination`/`-sdk`, so `simctl install` later refuses it ("has code for platforms:
     [iOS, arm64]... device can run: iOS-simulator") — confirmed live on both this app and the
     native CounterApp. Building directly with `xcodebuild build` avoids that mistagging.
   - `-configuration Release` — same Metro-bundler rationale as the Android build above: a
     Debug build needs Metro running; Release embeds the JS bundle so it runs standalone under
     Maestro.
   - `CODE_SIGNING_ALLOWED=NO` — skips code signing during the build (no signing identity
     needed on CI for a simulator build).
   - `find ... -name 'CounterRN.app'` locates the built `.app` bundle under the custom
     `-derivedDataPath`, and `envman add --key BITRISE_APP_DIR_PATH ...` exports it as an env
     var so later steps in this same workflow can reference it.
6. **`script@1.2.1`**, titled "Ad-hoc codesign the built app".
   ```bash
   codesign --force --deep --sign - "$BITRISE_APP_DIR_PATH"
   ```
   Ad-hoc signs (`--sign -`) the unsigned build from step 5. The inline comment explains why
   this step exists: `xcodebuild test` tolerates an unsigned app because its own harness does
   the launching, but Maestro launches the app via a bare `simctl launch`, which was denied by
   SpringBoard on iOS 18.x simulators for an unsigned app ("SBMainWorkspace" — confirmed live,
   same root cause as the `ios-maestro-e2e` native-app workflow). Ad-hoc signing fixes it.
7. **`bundle::ios_simulator_boot`** — Step bundle ([`bitrise/common.yml`](../bitrise/common.yml), see
   [`docs/BITRISE_CONCEPTS.md`](../docs/BITRISE_CONCEPTS.md) §7; previously an inline
   `script@1.2.1` titled "Boot simulator for Maestro"):
   ```bash
   xcrun simctl boot "Bitrise iOS default" 2>/dev/null || true
   xcrun simctl bootstatus "Bitrise iOS default" -b
   ```
   Boots the named simulator (ignoring an "already booted" error) and blocks until boot
   completes, so Maestro has a running device to target — mirrors the role
   `wait-for-android-emulator` plays in the Android workflow, but done by hand here since there
   is no equivalent "wait for iOS simulator" Bitrise step used in this workflow.
8. **`maestro-test@1.2.0`** — inputs: `app_path: $BITRISE_APP_DIR_PATH` (from step 5's
   `envman`), `flow_path: .../apps/react-native/maestro` (same flow directory as Android),
   `test_name: Maestro E2E (React Native / iOS)`, `maestro_version: 2.12.1`,
   `num_flaky_test_attempts: 1`, `additional_args: -e
   MAESTRO_APP_ID=org.reactjs.native.example.CounterRN` — the iOS bundle id, parameterizing the
   same flow files as the Android run (see §4.3 step 7 for the mechanism).
9. **`save-npm-cache@1.2.1`** — same as above.
10. **`deploy-to-bitrise-io@2.26.2`**, `is_always_run: true` — same as above.

## 5. Video recording

Two independent recording mechanisms are at play, both ultimately gated (directly or
indirectly) by the app-level `$RECORD_VIDEO` env (`all`\|`failures`\|`off`, default `all`):

- **Detox (`rn_detox_ios`)**: Detox has its own native artifact plugin with modes
  `all`\|`failing`\|`none`, driven by the `--record-videos` CLI flag on `detox test` (see
  `.detoxrc.js`'s `artifacts.plugins.video: { enabled: true }`, which only turns the plugin on —
  the actual mode is chosen per run by the flag, not hardcoded in the config). The workflow's
  script maps `$RECORD_VIDEO` onto Detox's vocabulary with a shell `case` statement
  (`all→all`, `off→none`, anything else (including `failures`) `→failing`).
- **Maestro (both `*-maestro-e2e-rn` workflows)**: recording is driven entirely from inside the
  flow files themselves — `counter_basic.yaml` and `counter_reset.yaml` both start with
  `startRecording: recording` and end with `stopRecording`. Maestro always records every run;
  there is no CLI flag in this config mapping `$RECORD_VIDEO` onto Maestro's behavior, so
  Maestro recordings are effectively always kept regardless of `$RECORD_VIDEO` (consistent with
  this repo's current default of `all`). Per the `maestro-test@1.2.0` step's own description,
  it exports each flow's `startRecording` video, screenshots, and logs attached to that flow's
  test case automatically — no extra attachment step is needed, unlike Detox.

### How Detox artifacts land on the correct Tests-tab test case

Bitrise's "naming attachments after test cases" convention requires a video/screenshot/log
file to be named `<classname>__<name>__<label>.<ext>` and live alongside (or be matched via
`search_pattern`/`base_path` by) the corresponding JUnit entry. Detox's own artifact plugin
does not name files this way by default, so this app overrides naming via a custom Detox
**pathBuilder**:
[`apps/react-native/e2e/bitrisePathBuilder.js`](../apps/react-native/e2e/bitrisePathBuilder.js),
wired into [`.detoxrc.js`](../apps/react-native/.detoxrc.js) (`artifacts.pathBuilder:
'./e2e/bitrisePathBuilder.js'`) and `artifacts.rootDir: './test-results'`.

Mechanism, read directly from `bitrisePathBuilder.js`:

```js
buildPathForTestArtifact(artifactName, testSummary) {
  if (!testSummary) return path.join(this.rootDir, artifactName);
  const { title, fullName } = testSummary;
  const key = clean(`${fullName.slice(0, -title.length).trim()} ${title}`);
  const ext = path.extname(artifactName);
  const label = path.basename(artifactName, ext).replace(/_+/g, '_').replace(/^_/, '');
  return path.join(this.rootDir, `${key}__${key}__${label}${ext}`);
}
```

- Detox's Jest reporter calls this once per artifact with `testSummary.fullName` (the full
  `describe > it` title, e.g. `"Counter app increments and resets"`) and `testSummary.title`
  (just the `it` title, e.g. `"increments and resets"`).
- `fullName.slice(0, -title.length).trim() + ' ' + title` reconstructs the full title in the
  exact same shape that `jest-junit`'s default settings also use for both the `classname` and
  `name` XML attributes of a test case (both default to the full qualified title) — this is
  the load-bearing detail: it is not approximating the name, it is reproducing jest-junit's own
  naming algorithm so the two independently-generated artifacts (the JUnit XML from
  `jest-junit` and the media filename from this path-builder) agree character-for-character.
- The same `key` is used for *both* the `classname` and `name` segments of the output filename
  (`${key}__${key}__${label}${ext}`), matching the convention's `<classname>__<name>__<label>`
  shape.
- `label` is derived from Detox's own artifact name (e.g. `initial_count`, `after_increment`,
  a screenshot/video/log base name), with repeated/leading underscores trimmed.
- Output files land under `test-results/` (same `rootDir` the JUnit file
  `test-results/detox-junit.xml` is written to), which is exactly the `base_path` /
  `search_pattern` that `custom-test-results-export@2.0.0` scans in `rn_detox_ios` step 6 —
  co-location under the same base path is required because, per the inline comment in
  `.detoxrc.js`, `custom-test-results-export` only matches attachment filenames under its
  `base_path`.

Note: [`scripts/reporting/attach_media_to_junit.py`](../scripts/reporting/attach_media_to_junit.py)
(a generic "attach a media file to JUnit XML by naming convention" helper used elsewhere in
this repo, e.g. for suite-level screen recordings or diff images against a first failure) is
**not** invoked anywhere in `react-native.yml`. The RN module achieves the same naming-convention
outcome natively through Detox's `pathBuilder` + jest-junit instead, since Detox already
produces one artifact file per test case; the Python script exists for cases where the test
framework being driven can't be told to name its own artifacts this way.

## 8. Adapting this to your own project

Minimal set to copy, and what must change:

- **`rn_jest_tests`** — copy as-is; only `workdir`/`working_dir` paths need to point at your
  app folder, and your `jest.config.js` needs the same `jest-junit` reporter block
  (`outputDirectory`/`outputName`) if you want Tests-tab output.
- **`rn_detox_ios`** — copy the workflow; you must:
  - Point `cocoapods-install`'s `source_root_path` and all `working_dir`s at your app.
  - Update `.detoxrc.js`: your scheme/workspace name, `binaryPath`, bundle id implicitly via
    your Xcode project, and simulator device type.
  - Decide whether you need the `applesimutils` Homebrew install (only needed if the stack
    image doesn't already have it).
  - Keep the Release-not-Debug choice unless your RN setup doesn't depend on Metro at runtime.
- **`bitrisePathBuilder.js`** — copy verbatim *only if* you also use jest-junit with its
  default naming (full qualified title as both `classname` and `name`). If your JUnit reporter
  names test cases differently (e.g. a custom `classNameTemplate`/`titleTemplate` in
  `jest-junit`'s options), the path-builder's `key` construction must be updated to match
  exactly, or attachments will silently fail to attach to the right test case.
- **Maestro workflows** — copy both; you must change:
  - `app_path` (Android APK output path / the iOS `.app` discovery logic) to match your
    project's build output layout.
  - The two `MAESTRO_APP_ID` values in `additional_args` to your Android package name and iOS
    bundle id, and add `appId: ${MAESTRO_APP_ID}` to the top of every flow file you copy.
  - The `xcodebuild`/`avd-manager` parameters (scheme, workspace, device profile, API level) to
    your project.
  - If you don't need true cross-platform flow reuse, you can drop the `${MAESTRO_APP_ID}`
    indirection and hardcode `appId:` per platform-specific flow file instead.

## 9. Troubleshooting / known issues

These are drawn from the file's own inline comments (documenting real failures hit while
building this config) plus a few observations worth flagging without changing the file:

- **Debug builds render nothing under Detox/Maestro.** Both the Android (`assembleRelease`)
  and iOS (`xcodebuild ... -configuration Release`) build steps carry explicit comments that a
  Debug build showed neither the `Count: 0` label nor the `increment_button` at all when driven
  externally, because Debug RN builds expect the Metro bundler to be running. If you ever
  switch these workflows to Debug for faster iteration, you must also stand up Metro (or embed
  the bundle some other way) or the Maestro/Detox flows will fail to find any UI element.
- **`xcode-build-for-simulator`'s `archive` action mistags the output for `ios-maestro-e2e-rn`.**
  The comment notes this was confirmed live twice (on this app and the native CounterApp): an
  archived build is tagged for the device platform regardless of `-destination`/`-sdk`, and
  `simctl install` refuses it. The workflow deliberately avoids that step and uses a raw
  `xcodebuild build` instead — if this step is ever "simplified" back to
  `xcode-build-for-simulator`, expect this failure to resurface.
- **Unsigned apps can't be launched by `simctl launch` on iOS 18.x.** `ios-maestro-e2e-rn`'s
  dedicated ad-hoc codesign step exists only because Maestro's underlying `simctl launch` was
  denied by SpringBoard ("SBMainWorkspace") for an unsigned app, even though `xcodebuild test`
  tolerates unsigned apps fine. Any workflow that builds with `CODE_SIGNING_ALLOWED=NO` and
  then drives the app via plain `simctl`/Maestro (rather than `xcodebuild test`) needs this same
  ad-hoc signing step.
- **`maestro test` has no `--app-id` flag.** Confirmed live failure ("Unknown option:
  '--app-id'") documented in `maestro/README.md` and inline in the flow files — the
  `-e MAESTRO_APP_ID=...` / `appId: ${MAESTRO_APP_ID}` pattern is the only way found to
  parameterize the same flow file across platforms with this step.
- **No `wait-for-iOS-simulator`-equivalent step is used; boot/wait is hand-rolled.** The
  `ios-maestro-e2e-rn` workflow boots and waits for the simulator with raw `xcrun simctl boot`
  + `bootstatus` rather than a dedicated Bitrise step (unlike the Android workflow's
  `wait-for-android-emulator`). This works but means any change to how the simulator is
  provisioned on this stack needs to be mirrored by hand in this script.
- **Hardcoded simulator name `"Bitrise iOS default"`.** `ios-maestro-e2e-rn` assumes a
  simulator with this exact name pre-exists on the stack image. If the stack ever renames or
  removes its default simulator, this workflow breaks with no fallback/discovery logic.
  `rn_detox_ios` sidesteps the exact-name issue by letting Detox's `devices.simulator` config
  in `.detoxrc.js` create/target an `iPhone 16` simulator by device type instead of a fixed
  name — but it has the same underlying assumption that an `iPhone 16` runtime is available on
  the stack, just expressed differently. Separately, `.detoxrc.js`'s own
  `apps['ios.release'].binaryPath` is a hardcoded relative path
  (`ios/build/Build/Products/Release-iphonesimulator/CounterRN.app`) tied to Detox's `build:`
  command's `-derivedDataPath ios/build` — consistent, but brittle if that build command is
  ever edited without updating `binaryPath` to match.
- **No explicit npm/Node version pin visible in this config.** The `npm@3.1.0` step's own docs
  note it uses corepack + `package.json`'s `packageManager` field (or an explicit
  `npm_version` input) to pin the npm version; this config sets neither, so it floats on
  whatever the stack's default npm/corepack resolves. `package.json` does pin
  `engines.node: ">= 22.11.0"` as a floor, not an exact version.
- **`maestro_version: 2.12.1` and `applesimutils`/CocoaPods versions are pinned/constrained
  inconsistently.** Maestro and the `restore-npm-cache`/`save-npm-cache`/`git-clone`/etc. step
  versions are all pinned exactly; CocoaPods itself is only range-constrained via the Gemfile,
  and `applesimutils` has no pinned version at all (`brew install wix/brew/applesimutils`
  always installs latest) — a future Homebrew release could silently change Detox simulator
  behavior on this workflow.
- **The Android Maestro workflow's release APK relies on the debug keystore.** The inline
  comment states the project's release `signingConfig` already points at the debug keystore
  "so it installs fine as-is" — convenient for CI, but anyone copying this workflow into a
  project with a real release signing config will need a different (debug-only) build
  variant/flavor for this purpose, or the release APK produced here won't be installable with
  only CI-available credentials.
